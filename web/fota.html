FOTA — Pi 5 / Linux ホスト試作

開発プレビュー

vehicle targetの署名済みアプリイメージをHTTPSまたはファイルから受け取り、署名と互換性を検証して非稼働スロットへ書き込みます。HTTPS配信はシステムCAでサーバー証明書を検証し、必要に応じて端末証明書による相互TLS認証も使えます。相互TLS時は証明書の転送を避けるためリダイレクトを許可せず、配信先はパッケージを直接返す必要があります。どちらの場合もパッケージ署名の検証は必須です。vehicleイメージは起動時に記録済みSHA-256と照合してから試験起動し、ヘルスチェックに合格すれば確定、失敗すれば元のスロットへ戻ります。個別ECU packageの現在の適用範囲は下記を参照してください。

このページは実装済みのPi 5/Linuxホスト経路を説明します。ブラウザ上のシミュレータ自体はFOTA更新しません。

Pi 5への初期セットアップ

リポジトリからFOTAランチャーとPiCar-X車両イメージをビルドします。署名ツールは別の保護されたリリース環境だけでビルドしてください。sdv-fota init は初期active slotに空でない通常の実行可能ファイルがあることを確認し、そのSHA-256を記録してから起動状態を初期化します。

cargo build --release --manifest-path rust/sdv-fota/Cargo.toml \
  --bin sdv-fota --bin sdv-fota-launcher
sudo install -m 0755 rust/sdv-fota/target/release/sdv-fota /usr/bin/
sudo install -m 0755 rust/sdv-fota/target/release/sdv-fota-launcher /usr/bin/
cargo build --release --manifest-path rust/sdv-picarx/Cargo.toml --bin sdv-picarx --bin sdv-picarx-health --bin sdv-picarx-discover
sudo install -m 0755 rust/sdv-picarx/target/release/sdv-picarx-health /usr/bin/
sudo install -m 0755 rust/sdv-picarx/target/release/sdv-picarx-discover /usr/bin/

署名コマンドは保護されたリリースホストで別にビルドします。

cargo build --release --manifest-path rust/sdv-fota/Cargo.toml \
  --features host-signing --bin sdv-fota-sign

アプリ実行用の非特権ユーザーを作成します。状態ディレクトリ、スロット、イメージ、boot metadataはroot所有にし、group/otherから書き込めないようにします。ツールはsymlinkの状態パスを拒否し、更新データと起動記録は排他的な一時ファイルからatomic renameで配置します。初期イメージにはPiCar-X用Rustホストを配置し、設定はスロット外に置きます。

sudo useradd --system --user-group --home-dir /nonexistent --no-create-home --shell /usr/sbin/nologin sdv-app
sudo install -d -o root -g root -m 0755 /var/lib/sdv-fota/slots/a /var/lib/sdv-fota/slots/b
sudo install -d -o root -g root -m 0755 /etc/sdv-picarx
sudo install -o root -g root -m 0644 rust/sdv-picarx/config/pi5.fota.disabled.example.json /etc/sdv-picarx/vehicle.json
sudo install -o root -g root -m 0755 rust/sdv-picarx/target/release/sdv-picarx /var/lib/sdv-fota/slots/a/sdv-image.bin
sudo sdv-fota init --state-root /var/lib/sdv-fota --active-slot a \
  --active-version 1.0.0 --security-version 1
printf 'SDV_FOTA_APP_UID=%s\nSDV_FOTA_APP_GID=%s\n' "$(id -u sdv-app)" "$(id -g sdv-app)" | sudo tee /etc/default/sdv-fota-launcher
sudo chmod 0644 /etc/default/sdv-fota-launcher

設定ファイルの場所をlauncherの環境へ追加します。

printf 'SDV_PICARX_CONFIG=/etc/sdv-picarx/vehicle.json' | sudo tee -a /etc/default/sdv-fota-launcher

以前の試作版から移行する場合は、旧launcherが稼働している間にactive imageを承認済みリリースと照合し、statusで確認したactive slotのdigestを登録します。これは現在のファイルをハッシュする操作なので、リリース由来の確認にはなりません。trial中は登録できません。

sudo sdv-fota record-active-integrity --state-root /var/lib/sdv-fota --slot a

例の設定は前進モーター出力をゼロにしています。GPIO chip pathとモーター・操舵校正を実車で確認するまで、forward powerを有効にしないでください。

署名鍵の信頼設定

リリース環境の sdv-fota-sign が表示する公開鍵を、root所有の /etc/sdv-fota/trusted-keys に登録します。秘密鍵はPiへコピーしません。

署名seedはリリース環境の通常ファイルに保管し、Unix modeを 0600 にします。署名ツールはgroup/otherから読めるseedを拒否します。

sudo install -d -o root -g root -m 0755 /etc/sdv-fota
PUBLIC_KEY_HEX='<key printed by sdv-fota-sign>'
printf '%s %s\n' 'release-2026' "$PUBLIC_KEY_HEX" | sudo tee /etc/sdv-fota/trusted-keys
sudo chown root:root /etc/sdv-fota/trusted-keys
sudo chmod 0644 /etc/sdv-fota/trusted-keys

ファイルは1行に key-id public-key-hex を記載します。installerはroot所有で、group/otherから書き込めない通常ファイルだけを受け付けます。

更新と試験起動

リリース環境でパッケージを作成し、Piで署名済みパッケージを導入します。

chmod 0600 /secure/release.seed
sdv-fota-sign --seed /secure/release.seed --key-id release-2026 --target vehicle \
  --version 1.1.0 --security-version 2 --trial-ms 5000 --config-schema 1 \
  --signal-if-version 1 --image sdv-image.bin --output update.sdvf

sudo sdv-fota install-url --state-root /var/lib/sdv-fota \
  --url https://updates.example/vehicle/update.sdvf --target vehicle \
  --config-schema 1 --signal-if-version 1

# 相互TLSが必要な配信先では端末証明書と秘密鍵も指定
sudo install -d -o root -g root -m 0750 /etc/sdv-fota/tls
sudo install -o root -g root -m 0644 device.crt /etc/sdv-fota/tls/device.crt
sudo install -o root -g root -m 0600 device.key /etc/sdv-fota/tls/device.key
sudo sdv-fota install-url --state-root /var/lib/sdv-fota \
  --url https://updates.example/vehicle/update.sdvf --target vehicle \
  --config-schema 1 --signal-if-version 1 \
  --client-cert /etc/sdv-fota/tls/device.crt --client-key /etc/sdv-fota/tls/device.key
sudo sdv-fota status --state-root /var/lib/sdv-fota
sudo sdv-fota verify-images --state-root /var/lib/sdv-fota
sudo systemctl restart sdv-fota-launcher.service

相互TLSのクライアント鍵は実行ユーザー所有で、group/otherから読めず書き込めない通常ファイルを指定してください。証明書と鍵は両方指定します。配信認証が成功しても、Ed25519署名と互換性の検証は省略されません。

launcherは起動対象のSHA-256を照合し、manifestの試験時間内に車両イメージを sdv-app として起動します。trial候補には SDV_TRIAL_SLOT が渡され、PiCar-Xランタイムはtrial中すべてのアクチュエータ指令をゼロに保ちます。同じユーザーで動く sdv-picarx-health は最近の制御周期成功に加え、推定速度とスロットル要求が設定した停車許容値内にある場合だけreadyを返します。最大2秒間health成功とプロセス稼働が続いてからtrial slotを確定し、候補イメージの欠落、digest不一致、移動検出、health途絶、早期終了はrollbackします。確定後launcherは安全モードのプロセスを停止し、systemdが確定slotを通常モードで再起動します。statusはactive/trial両slotのdigest照合状態と直近trialの結果・slot・versionを表示します。サービス例は deploy/systemd/sdv-fota-launcher.service にあります。launcherはUID/GID切替に必要な2つのcapabilityだけを持ちます。

launcherは従来の位置引数形式を維持し、target-aware modeではvehicleとECUを分けて扱います。legacy positional formはvehicle base root専用です。/var/lib/sdv-fota/ecus/engineのようなECU rootをpositional引数に渡すと従来のtrial semanticsで動くため、必ずtarget-aware ECU formを使います。vehicle targetは既存のtrial health/commit/rollback semanticsを維持します。Engine、Brake、Steeringは固定state root ecus/<target> のactive slotだけを起動し、--health-program/--health-argを受け付けません。active-only APIは select_for_boot()を呼ばず、pending trialの boots_left とmetadataを変更しません。子processから SDV_TRIAL_SLOT と SDV_IMAGE_PATH を除き、trial health、commit、rollbackを行いません。candidate worker healthやroute cutoverはcoordinator統合の次段階です。ECU targetにはtargetと一致する --ecu 引数が一つ必要です。繰り返し指定する --app-arg はshellを介さず個別argvで渡ります。

sdv-fota-launcher --state-root <base-dir> --target vehicle \
  --health-program <vehicle-health-check> [--health-arg <arg> ...] [--app-arg <arg> ...]

sdv-fota-launcher --state-root <base-dir> --target engine \
  --app-arg --ecu --app-arg engine [--app-arg <worker-argument> ...]

ECU用の SDV_FOTA_ECU_APP_UID/GID と SDV_FOTA_ECU_APP_GROUPS は車両用 SDV_FOTA_APP_* と分離し、ECU supplementary groupsは既定で空です。launcherは空のときも継承groupsを消します。ECU用には専用の非root UID/GIDを設定してください。同じUIDを使う場合はOS権限の分離になりません。ECU固定rootの親 ecus はlauncher所有の実ディレクトリが必要で、symlinkは拒否します。引数はroot所有のservice設定に固定し、署名manifestから読みません。

既存の sdv-picarx-health はvehicle runtime用で、ECU workerのhealth checkではありません。installed systemd unitもvehicle target専用です。別のshadow candidate serviceはpending imageを専用socketで起動して一致するresponseを検証しますが、active-only launchとは別機能です。出力hold、安定candidate health、route cutover、cutover後のcommit/rollbackには未接続です。このshadow結果だけでcandidate出力を実車へ使えません。

statusは診断表示なのでdigest不一致でも終了コード0です。監視や更新前ゲートで検証結果を終了コードに反映する場合は sudo sdv-fota verify-images --state-root /var/lib/sdv-fota を使ってください。activeイメージとpending trialイメージのdigestがすべて一致するときだけ成功します。

停車ゲートは外部の状態推定値に依存するソフトウェア判定で、物理的な停止を独立検証しません。信頼できるセンサー推定を使い、trial中は車両を機械的に固定してください。

launcherの自動復旧が動かない状態でtrialが残った場合は、管理者が sudo sdv-fota rollback-trial --state-root /var/lib/sdv-fota を実行できます。現在のactive slotは維持され、次回launcher起動時に使われます。このコマンドは稼働中プロセスを停止しないため、実車を止めてから実行し、その後launcherを再起動してください。

試験起動中は外部の入力・車両状態推定プロセスが /run/sdv-picarx/input.sock へ継続送信する必要があります。各センサ取得時に time.monotonic_ns() の時刻と増加するsequenceを付けます。古い状態、過剰な入力、停車許容値を超える推定速度やスロットル要求は安全停止またはtrial失敗になります。

仮想ECUごとのパッケージstage

Engine、Brake、Steeringは --target で選び、それぞれ独立したA/B slot、active version、security counter、trial metadataを持てます。車両全体の既存状態はbase path直下、個別ECUは固定された ecus/engine、ecus/brake、ecus/steering の下に保存します。各ECUの既存active imageを先に用意して、個別に init してください。

sudo install -d -o root -g root -m 0755 /var/lib/sdv-fota/ecus/engine/slots/a \
  /var/lib/sdv-fota/ecus/engine/slots/b
sudo install -o root -g root -m 0755 engine-current.bin \
  /var/lib/sdv-fota/ecus/engine/slots/a/sdv-image.bin
sudo sdv-fota init --state-root /var/lib/sdv-fota --target engine \
  --active-slot a --active-version 1.0.0 --security-version 1

sdv-fota-sign --seed /secure/release.seed --key-id release-2026 --target engine \
  --version 1.1.0 --security-version 2 --trial-ms 5000 --config-schema 1 \
  --signal-if-version 1 --image engine-update.bin --output engine-update.sdvf
sudo sdv-fota install --state-root /var/lib/sdv-fota --package engine-update.sdvf \
  --target engine --config-schema 1 --signal-if-version 1
sudo sdv-fota status --state-root /var/lib/sdv-fota --target engine
sudo sdv-fota verify-images --state-root /var/lib/sdv-fota --target engine

署名manifestのtargetとinstall CLIのtargetが一致しなければinstallは拒否されます。省略したtargetは既存互換の vehicle を選びます。個別ECUのinactive slotとtrial metadataは独立しています。installed systemd unitは引き続きvehicle imageを起動します。launcherのactive-only formはdigest検証済みのactive imageを起動し、pending trial metadataは変更しません。ECU packageをstageしただけではworkerは更新されません。

sudo install -m 0644 deploy/systemd/sdv-fota-launcher.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now sdv-fota-launcher.service

適用範囲

Pi/Linux runtimeは既定で既存のin-process ECU経路を使います。coordinatorがworker processをspawnする既存モードは、vehicle configへ次の設定を追加します。

"virtual_ecu_workers": {
  "binary": "/usr/bin/sdv-picarx-ecu-worker",
  "socket_directory": "/run/sdv-picarx/workers"
}

systemd管理のworkerへ接続する場合は mode: external を明示して binary を省略し、coordinatorが既存のEngine、Brake、Steering socketを使います。candidate_socket_directory を設定するとshadow candidate用の別coordinator socketもbindします。省略したmodeは互換性のため spawn なので、binaryの指定漏れでexternalへ切り替わることはありません。candidate通信はactive応答socketから分離され、active worker readinessと出力には影響しません。

sudo install -o root -g root -m 0644 rust/sdv-picarx/config/pi5.external-workers.disabled.example.json /etc/sdv-picarx/vehicle.json
sudo install -m 0644 deploy/systemd/sdv-fota-launcher.service /etc/systemd/system/
sudo install -m 0644 deploy/systemd/sdv-fota-ecu@.service /etc/systemd/system/
sudo install -m 0644 deploy/systemd/sdv-fota-ecu-candidate@.service /etc/systemd/system/
sudo install -m 0644 deploy/systemd/sdv-fota-workers.target /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl stop sdv-fota-workers.target
sudo systemctl restart sdv-fota-launcher.service
sudo systemctl enable --now sdv-fota-workers.target

各serviceは sdv-fota-launcher --target engine|brake|steering のactive-only経路を使い、固定したmatching --ecu とsocket argvを渡します。host launcher起動直後にcoordinator socketがまだ無い場合、workerはbounded retryし、host coordinatorも全worker socketのreadinessを待ってからruntime cycleを開始します。worker serviceはhost launcherのrestartに追随します。

最初のsocket権限設計ではroot所有の /etc/default/sdv-fota-launcher で SDV_FOTA_ECU_APP_UID/GID を既存 sdv-app の数値UID/GIDにし、SDV_FOTA_ECU_APP_GROUPS= を空にします。workerにgpio/i2c supplementary groupは渡しません。同じUIDを共有するため、この構成はOS privilege isolationではありません。coordinatorはsensor/inputとGPIO/I²C actuatorを所有し、全active workerのECU ID・peer path・boot内単調増加cycle IDが一致したresponseを期限内にそろえたときだけ出力します。active worker欠落、timeout、malformed/stale response、期限超過ではsafe-stopし、partial/stale commandを適用しません。

Engineのpending imageをshadow起動

external configでcandidate directoryを有効にし、ECU packageをstageしてdigestを確認した後、対象ECUだけcandidate serviceを起動します。以下はEngineだけを対象にする例です。Brake/Steering workerはactiveのまま動きます。

sudo sdv-fota status --state-root /var/lib/sdv-fota --target engine
sudo sdv-fota verify-images --state-root /var/lib/sdv-fota --target engine
sudo systemctl start sdv-fota-ecu-candidate@engine.service
sudo journalctl -u sdv-fota-launcher.service -f

candidateは /run/sdv-picarx/candidates/engine.sock と別coordinator socketを使い、同じcycle inputを受けて応答を検証します。active応答の検証後、hostは固定snapshotをcapacity-oneの try_send queueへ渡すだけで、candidateのfilesystem確認、datagram送受信、timeout処理、journal出力は専用threadが行います。queue満杯または期限切れsnapshotはshadow cycleだけをskipし、hostはcandidate処理を待ちません。candidate coordinatorの初期化失敗もactive worker起動を妨げません。応答したcommand/aliveは破棄し、active routeと実車出力は変えません。candidate timeout、protocol違反、重複応答、socket差替えはcandidateだけをfailedにし、active cycleを止めません。host launcher journalの Ready は一回の一致応答を意味するだけで、sdv-picarx-healthの車両healthとは別の診断であり、安定health判定や昇格承認ではありません。

shadow起動はtrialの boots_left、active slot、trial metadata、digestを変更せず、commit/rollbackもしません。candidateを停止してからreplacement installまたは管理者rollbackを行ってください。出力hold、atomic route cutover、production route確認後のcommit/rollbackは次段です。candidate出力を実車へ使う手順はまだありません。

sudo systemctl stop sdv-fota-ecu-candidate@engine.service
sudo sdv-fota rollback-trial --state-root /var/lib/sdv-fota --target engine

externalから戻す場合はhostとworker targetを両方停止し、targetをdisableしてからroot-owned configをspawnまたはin-process用に差し替え、hostだけ再起動します。externalへ戻す場合も、hostがactiveなら先にhostとtargetをstopし、configを置いてhostをstart/restartして再読込させてからtargetをenable/startします。targetだけ停止した状態でexternal hostを動かすとworkerが欠落し、hostはsafe-stopしてrestartを繰り返します。

sudo systemctl stop sdv-fota-launcher.service sdv-fota-workers.target
sudo systemctl disable sdv-fota-workers.target
# install the root-owned spawn-mode or in-process vehicle config
sudo install -o root -g root -m 0644 /path/to/vehicle-config.json /etc/sdv-picarx/vehicle.json
sudo systemctl start sdv-fota-launcher.service
  • 車両全体は既存互換の vehicle A/B imageを使います。Linux CLIは engine、brake、steering の個別signed packageを独立stageし、target別trial metadataを記録できます。ECU worker serviceはactive imageだけを起動し、別candidate serviceはpending imageをshadow検証します。actuator output hold、安定health、socket route cutover、route確認後のcoordinator管理commit/rollbackはまだ未接続です。
  • Pi OS、EEPROM、boot partition、raw deviceは書き換えません。
  • Linux上の自動テストはありますが、Pi 5実機でのGPIO/I²C、入力・状態推定プロセス、校正、電源断・再起動・復旧試験はまだ必要です。
  • AUTOSAR Classic実機には、採用BSW/MCAL、DCM、NvM、Flash、Bootloaderへの個別接続が必要です。
