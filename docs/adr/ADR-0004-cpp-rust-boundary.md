# ADR-0004: C++ と Rust の境界（実機に載るソフトは何で書くか）

## Status

Proposed（下書き 2026-11-11）。**「決めてほしいこと」に答えをもらってから** Accepted にして「決定事項」を追記する。それまでの当面の運用は「暫定の運用」に書いた。

> 番号について: ADR-0003 改訂1 と ADR-0005 が、この ADR を「C++/Rust の境界の整理」として予約していた。

## Context

### 当初の方針（2026-10 の議論）
- 「実機に載るソフト（SWC、Model、Watchdog、ECU のフェイルセーフ、Config の検証、NVM、フレームの符号化）は **C++**、シミュレーション基盤（仮想バス、故障注入、シナリオ、WASM/GUI）は **Rust**」と分け、**二重管理を避ける**。
- 理由: 作者は「書きたいコードはまだ C++ のほうが多い」。実機（Raspberry Pi）にそのまま載る作りにしたい。
- 実機に載るコードの移植ルール（インスタンス化・ヒープなし・例外なし・時刻/ファイルは Platform API 経由）と、C ABI の Platform API で Rust が C++ を呼ぶ形を想定していた。

### 実際に起きたこと（2026-11-11 の `main` を測定）
実機向けのコードは、ほぼすべて **Rust** で書かれた。

| 場所 | 言語 | 行数（`src/`） | 役割 |
|---|---|---|---|
| `src/`（C++） | C++ | 約 1,060（テスト約 1,370） | 1 プロセス・1 RTE の参照実装。基準ログ（golden）の生成元 |
| `rust/sdv-core` | Rust | 約 4,700 | シミュレータ本体、ECU 分割・仮想バス、フェイルセーフ、Config/NVM、シナリオ、試験適用、**実機向け `VehicleRuntime`**、WASM |
| `rust/sdv-sec` | Rust（`no_std`、C ABI） | 約 370 | SHA-256、Ed25519 検証、フレーム MAC |
| `rust/sdv-fota` | Rust（コアは `no_std`・allocator なし、C ABI） | 約 7,700 | FOTA（署名済みパッケージ、A/B、trial、Pi 5 の導入・起動、Classic 向け C ABI） |
| `rust/sdv-picarx` | Rust | 約 6,800 | Pi 5 + PiCar-X のプラットフォーム（Robot HAT、I2C、GPIO、車両ホスト、仮想 ECU ワーカー） |

- C++ にあって Rust にないものは事実上ない（C++ の BSW は TimeBase・Diag・Logging の最小実装）。バス、ECU 分割、フェイルセーフ、Config/NVM、試験適用、FOTA は Rust にしかない
- 実機で動く経路（Pi 5 の `VehicleRuntime` → `sdv-picarx`）に、**C++ は一行も入っていない**
- CI は Pi 5 の実ターゲット（aarch64）で Rust をビルド・テストしている。C++ は x86-64 のみ

### 二重管理の実態
- 二重になっているのは **Model 層（純粋関数）と SWC、Safety の判定**: Engine / Brake / Steering / VehicleDynamics の Model、Watchdog の判定（`safety_logic`）。Rust 側は `model.rs`・`swc.rs`・`safety.rs`（合わせて約 450 行）
- 式の写しの例: タイヤの限界 `atan(L·μ·g/v²)` が C++ の `StepLateral` と Rust の `model.rs` に**同じ式で 2 つある**（ADR-0003 改訂1 が「暫定の写し」と書いたもの）
- 同期の仕組みは **基準ログ（golden）の全行比較**（C++ の出力 4 本を Rust が再現する）。ただし golden が見るのは「デモ走行 + 故障注入 3 パターン」の挙動だけで、**Model の個々の関数の仕様は見ていない**（たとえば、摩擦の限界は基準の走行では当たらない: 横加速度の最大が 0.21 G で、上限の 0.6 G に届かない）。実際に結合テストの変異で、「基準ログは通るのに挙動が壊れている」ことが起こりうると確認している
- **当初の「新しい機能は C++ だけに入れる」という暫定の規則は、守られていない**（試験適用・FOTA・picarx はすべて Rust にだけ入った）

### 技術的に分かっていること
- C++ → WASM は wasi-sdk（clang）でビルドできた（Emscripten は取得できなかった）。ただし **Rust の cdylib に C++ を静的にリンクして WASM にする**ことは試していない
- Rust → C ABI → C/C++ は、`sdv-sec` と `sdv-fota` で実装・テスト済み（C の smoke テストが CI にある）。逆向き（Rust から C++ を呼ぶ）は未実装
- aarch64 のクロスビルドと `qemu-user` でのテストは CI にある（C++ では未実施）

## 選択肢

### 案 A: Rust を本番の唯一の実装にする。C++ は参照実装・golden の生成元に縮小する
- 良い点: 実態に合う。Model / SWC の二重管理が（時間をかけて）なくなる。FOTA・picarx・WASM と同じ言語で、ビルドも FFI も増えない
- 悪い点: 「C++ で書きたい」という当初の希望とは逆。C++ の実装は価値が下がる（golden の生成元・読み比べ用に残す）。AUTOSAR Classic の SW-C は C が前提なので、Classic 向けの再利用には C ABI（`sdv_fota.h` の方式）が要る

### 案 B: C++ を ECU ソフトの正にし、Rust は C ABI で呼ぶ（当初案）
- 良い点: 当初の希望どおり。Model・SWC・フェイルセーフ・Config の検証が C++ 一本になる。Classic 向けの再利用に近い
- 悪い点: **最も大きい作業**。Rust の `sdv-core`（Config、NVM、フェイルセーフ、試験適用、`VehicleRuntime`）を C++ に移し、`sdv-picarx` / `sdv-fota` から C++ を呼ぶ。WASM は C++ を Rust にリンクする方法が未検証。FFI の `unsafe` 境界が増える。すでに実機向けの経路が Rust で動いているので、手戻りが大きい

### 案 C: 層で分ける — 「アルゴリズム（純粋関数）は C++、基盤は Rust」
- Model（Engine / Brake / Steering / VehicleDynamics の式、Watchdog の判定、タイヤの限界など）を **C++（C 互換の部分集合）一本**にし、Rust が C ABI で呼ぶ。SWC・RTE・ECU・バス・Config・NVM・FOTA・Platform は Rust のまま
- 良い点: 「書きたいコード（制御のアルゴリズム）は C++」を満たしつつ、すでにある Rust の基盤を活かせる。二重管理の中心（式の写し）が消える。純粋関数なので移植性が高く、Classic の SW-C にも近い
- 悪い点: ビルドが複雑になる（`cc` crate、aarch64 のクロス、**WASM にリンクできるかが未検証**）。Model の呼び出しごとに FFI を挟む。Model が小さい（約 250 行）ので、効果に比べて仕組みが重くなるおそれがある

### 案 D: 現状維持 — 二重管理 + golden
- 良い点: 追加の作業がない
- 悪い点: 上の「二重管理の実態」のとおり、golden が見ない部分で**黙って食い違う**。実際、新しい機能は Rust だけに入っていて、C++ は取り残されつつある

### 案 E（案 D の補強）: 共有テストベクタで契約を実行可能にする
- Model の各関数について「入力 → 期待する出力」の**テストベクタを JSON で 1 つ**置き、C++ と Rust の**両方のテストがそれを読む**。どちらかが式を変えると赤くなる
- 良い点: 安い（FFI もビルドの変更もない）。二重管理は残るが、**食い違いを機械的に検出できる**。案 A / C のどちらに進んでも無駄にならない
- 悪い点: 二重管理そのものは消えない

## 暫定の運用（決まるまで）
1. **Model の式を変えるときは、C++ と Rust を同じ PR で変える**。片方だけの変更は入れない
2. **新しい機能は Rust に入れる**（実機で動く経路が Rust のため）。C++ に入れるのは、基準ログの再現に必要な範囲だけ
3. **案 E の共有テストベクタ**を先に入れる（案 A・C のどちらでも使える）
4. ECU ソフトの**移植ルール**は、すでに `sdv-sec` と `sdv-fota` のコアが従っているものを明文化する: ヒープなし・グローバル状態なし（呼び出し側が渡す領域だけを使う）、時刻とファイルは Platform（trait / コールバック）経由、`std` を使う層と使わない層を feature で分ける、公開する C ABI は `include/*.h` に置いてテストで実装と突き合わせる

## 推奨
**当面は 案 E（共有テストベクタ）を入れ、そのうえで案 A か 案 C かを、小さな検証（スパイク）で決める。** 案 B は、実機の経路がすでに Rust にあるので勧めない。

- 案 C の決め手は「Rust の WASM に C++ をリンクできるか」と「aarch64 のクロスビルドの手間」。これを 1〜2 日のスパイクで測る（C++ の Model を C ABI の静的ライブラリにして、`sdv-core` から 1 関数だけ呼ぶ）
- スパイクが通り、**オーナーが今後もアルゴリズムを C++ で書きたい**なら 案 C。そうでなければ 案 A（C++ は golden の生成元に縮小）

## 決めてほしいこと
1. **今後、制御のアルゴリズム（Model、Watchdog の判定など）を自分で書くとき、C++ で書きたいか、Rust で書いてよいか**（案 C か 案 A かを分ける）
2. C++ の参照実装は**完全なシミュレータとして残す**か、Model + golden の生成元に**縮小**してよいか
3. `sdv-sec` は、Rust のまま C ABI で配る（現状）でよいか（ADR-0005 追加の確認事項 C）。推奨: 現状維持
4. 上の「暫定の運用」の 1〜4 を、この ADR が Accepted になるまでの規則にしてよいか

## Consequences（案 E + 後続の判断としたとき）
- 良い点: 食い違いを機械的に検出できるようになる。方針を決めるための事実（WASM へのリンク、aarch64）が手に入る
- 悪い点: 当面は二重管理が残る。テストベクタの整備に手間がかかる
- 後続: 案 A か 案 C に決めたら、この ADR を Accepted にして「決定事項」を追記し、`README.md` の「C++ と Rust の役割」の表と `docs/design/07_ecu_architecture.md` §9 を更新する。ADR-0003 改訂1 の「暫定の写し」の記述を解消する
